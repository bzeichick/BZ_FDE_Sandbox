# Decision log

One row per architectural decision, with the option you rejected and why.

> **Week 5 asks you to defend your agent architecture against the alternatives.**
> **Week 10's handoff doc is largely this file.** Both are much easier if you
> wrote the reasoning down while you still remembered it.

A decision without a rejected alternative is not a decision, it is a default.
If you cannot name what you did not do, you did not choose.

| 1 | Pipeline: one model call that fills responses, then schema validation | An agent that decides its own next step such as looking up customer profiles or the TMS mid-run | Every order goes through the same steps and all fields come from the order intake, the schema catches malformed output and possible outcomes are a closed list. A single model call per order keeps the cost per order fixed and predictable and gives the same path for the same input so results can be compared directly with test data | If roughly 15% of real orders end up with a question to the customer that is already captured such as address, usual pickup location, rate from lane history; then looking things up mid-order is the job, and an agent with lookup tools would be worth it. This could be measured from the questions field across trial orders | The order text alone often isn't enough because real orders use facility names instead of addresses or rely on a customer's typical pickup location. An agent that could lookup profiles, addresses, load history could fill it in itself with fewer questions back to the customer |
| 1 | Don't ask the customer for a missing delivery date, but flag it to be scheduled | Asking every customer | Matches how the order desk actually works by scheduling for the customer and advising them | If receivers start rejecting deliveries because of real deadlines that weren't communicated | Some customers' receivers have hard deadlines that only the customer knows |
| 1 | Record the customer's date as a ready date; leave pickup to be scheduled, and record temperature as a range | Treating the customer's "ready Friday" or requested date as the pickup date, and temperature as a single max | Demo feedback: the company consolidates pickups on its own scheduled runs, so a ready date entered as a pickup date would mislead whoever reads the TMS; frozen is a 0 to -10 range, not one number. Golden #1 was rejected on exactly this and rewritten. | If customers' ready dates turn out to be firm pickup commitments for some accounts | For some shippers the dock schedule is fixed, so their date really is the pickup date and flagging it adds work |
| 2 | Model/endpoint: hosted, direct to Anthropic's API (no gateway), anthropic/claude-sonnet-5, for both synthetic data generation and the Week 1 app | Local open weights (LiquidAI/LFM2.5-350M on my laptop); a company gateway | Speed: same 80-token generation took 2.61 s hosted (~31 tok/s) vs 48.17 s local, CPU-only on MacBook Pro (Apple M1 Pro, 16 GB), ~1.7 tok/s (measured). Quality: local output repeated words and drifted off-topic (measured, read by me). Cost: ~$10 for ~225 generation calls on Oct 19, ~4.5¢ per call (measured, Anthropic console); per-token Price: $2 per million input tokens, $10 per million output tokens (looked up, claude.com/pricing, Oct 19 2026). Per call ~4,000 input and 3,000–6,700 output tokens, 60–80% of output is reasoning (measured, provider-reported usage). Only fictionalized seeds and invented rows are sent, never real orders (constraint — met by design). Hosted is faster and writes better rows (preference). | If US Perishables or a shipper requires order data never leave our network, hosted fails outright and a local or private endpoint becomes required; or if a served local model (e.g. vLLM on a GPU) comes within ~2–3× of hosted latency at usable quality | The hosted model rejected temperature=0.7, exposes no logits and takes no seed, so a run cannot be reproduced exactly; a local model gives full sampler control and keeps data in-house. The local figure is a worst case: the test loop had no KV cache |
| 2 | Dedupe at character 4-gram Jaccard 0.7 on the order text | A lower threshold (0.5), which would drop look-alike orders that differ on the action, e.g. "book the Fresno load Friday" vs "cancel the Fresno load Friday"; a higher one, which drops almost nothing | At 0.7, 0 of 553 rows were dropped in the full run, and 0 of 101 in two smoke runs (measured). The most similar pair of the 551 valid rows scores 0.47; 0 pairs reach 0.5 and 105 pairs reach 0.4 (measured). Reading the top pairs, they are different orders that share a template and subject-line format (a quote vs. a new order, different lanes and dates), not rewordings of one order, so lowering the threshold would delete real test cases rather than paraphrases | If the dropped pairs at a threshold differ only in wording, lower it to remove paraphrases; if they differ on an action, date or temperature, the threshold is removing real test cases, so keep or raise it | Character n-grams miss paraphrases ("10 pallets" vs "ten pallets") and over-match rows that share long boilerplate like email signatures and Gmail headers; embeddings (Week 3) would catch the first case |
| 2 | Generate in two runs: ENTERABLE crosses all five axes (540 combinations); ROUTE_TO_PERSON crosses only arrival × reason (12) | Crossing every axis (~2,400 combinations); trimming values until the full cross was affordable; one combined dict | Routing is what the decline run tests and field extraction is already covered by ENTERABLE, so crossing declines with temperature and date adds cost, not coverage. Every axis is crossed only where it changes the expected output | If route-to-person rows turn out to mislabel fields (not just routing), the decline run needs temperature and date crossed too | Declines in real mail still carry temperatures and dates; a model that routes correctly but extracts those fields badly is not tested by the small run |
| 2 | Generation settings: 2 seeds per prompt matched to the arrival format; 1 row per call; max_tokens 16000; one retry for a combination that returns nothing; provider-default sampler and reasoning | Always showing the first 3 goldens; 3 rows per call; max_tokens 8000 | The first 3 goldens never showed the PO-attachment format and anchored every row on one customer's layout. At 8000 tokens, 3 of 50 long-thread combinations returned nothing because reasoning used the budget (measured: up to 5,324 reasoning tokens on one call). With 16000 plus one retry: 50 of 50 combinations produced a row (measured) | If empty combinations come back at scale, or reasoning cost dominates enough to justify turning it down and re-validating the prompt | Leaving reasoning at the default makes cost and run time vary per call, and without a seed no run is exactly reproducible |
| 2 | Keep synthetic_v1 despite repeated invented details; fix before Week 3 by having code, not the model, choose each row's PO number, sender, company and send time | Regenerating now (~6 hrs, ~$25); accepting the repetition permanently | Measured across 551 rows: 67% sent at 8:14–9:15, 42% from a "Bright…" company, 31% from a sender named Dana, and PO# BH4471 appears in 29 rows. Each call invents independently and the model reuses its favourites; row-level dedupe can't see it because the orders differ in substance. Coverage of the axes is intact | Week 3 retrieval or Week 4 scoring keys on reference numbers, so duplicate POs will collide; that's the deadline for the fix | A dataset where a third of senders share a name is less realistic, and Step 6 reviewers may judge every row by it |
| 2 | "REFER" alone means refrigerated (standard 34–38 °F, flagged TEMP_STANDARD_ASSUMED); "REFER (FROZEN)" means frozen | Treating "REFER" as ambiguous and asking the customer every time | Order-desk convention at the freight broker; found while reading synthetic rows where the generator labelled REFER as refrigerated but inconsistently flagged it | If the order desk reports REFER orders that turned out to be frozen loads | A reefer trailer runs frozen or refrigerated, so a bare "REFER" from an unfamiliar shipper could mean either; asking costs one email, a wrong setpoint costs a load |
| 2 | A correction later in the thread that changes the pallet count or weight makes any earlier rate stale: the rate is left empty and flagged for a re-quote | Keeping the last rate quoted or accepted in the thread | Step 6: the sales director flagged order 2 ("New rate for the 5 pallets, instead of the 6-pallet rate"); rates are priced on the count, so a rate agreed for one count doesn't carry to another. The tool's output for order 2 happened to be right (that rate was never accepted), but no rule required it | If rates turn out to be flat per lane for small count changes | Re-quoting a one-pallet change adds an email the customer may not want |
| 2 | Temperature mode includes "dry" (no temperature range): in the charter now; schema, generation prompt and app in the Week 3 regeneration | Frozen and refrigerated only, with anything else rejected by the schema | Step 6: the operations reviewer said every order must be stated as "Dry" or "Temp Controlled" (order 16), and US Perishables does move dry freight (confirmed by me). The 2 rows the schema rejected for "dry"/"ambient" were the schema being stricter than real orders, not the model being wrong | If dry loads turn out to be rare enough to route to a person instead of entering | "Ambient" may or may not mean the same as dry here; and a "no temperature" question now has three answers, not two |
| 2 | Order status (potential order at the quote stage vs. valid order with an approved rate) is a missing output field; deferred to Week 3/5 | Treating every quote as an order, as the charter does today | Step 6: the operations reviewer sorted all 20 orders this way, and what's needed differs: pickup date, location, temperature and commodity to quote; dispatch steps once the rate is approved | If the order desk enters quotes and orders identically in the TMS | Adding a status field means the model must judge rate approval from the thread, which is another label to get right |
