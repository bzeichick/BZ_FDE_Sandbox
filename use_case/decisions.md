# Decision log

One row per architectural decision, with the option you rejected and why.

> **Week 5 asks you to defend your agent architecture against the alternatives.**
> **Week 10's handoff doc is largely this file.** Both are much easier if you
> wrote the reasoning down while you still remembered it.

A decision without a rejected alternative is not a decision, it is a default.
If you cannot name what you did not do, you did not choose.

| 1 | Pipeline: one model call that fills responses, then schema validation | An agent that decides its own next step such as looking up customer profiles or the TMS mid-run | Every order goes through the same steps and all fields come from the order intake, the schema catches malformed output and possible outcomes are a closed list. A single model call per order keeps the cost per order fixed and predictable and gives the same path for the same input so results can be compared directly with test data | If roughly 15% of real orders end up with a question to the customer that is already captured such as address, usual pickup location, rate from lane history; then looking things up mid-order is the job, and an agent with lookup tools would be worth it. | 1 | Record the customer's date as a ready date; leave pickup to be scheduled, and record temperature as a range | Treating the customer's "ready Friday" or requested date as the pickup date, and temperature as a single max | Demo feedback: the company consolidates pickups on its own scheduled runs, so a ready date entered as a pickup date would mislead whoever reads the TMS; frozen is a 0 to -10 range, not one number. Hosted is faster and writes better rows (preference). | If US Perishables or a shipper requires order data never leave our network, hosted fails outright and a local or private endpoint becomes required; or if a served local model (e.g. vLLM on a GPU) comes within ~2–3× of hosted latency at usable quality | The hosted model rejected temperature=0.7, exposes no logits and takes no seed, so a run cannot be reproduced exactly; a local model gives full sampler control and keeps data in-house. The local figure is a worst case: the test loop had no KV cache |
| 2 | Dedupe at character 4-gram Jaccard 0.7 on the order text | A lower threshold (0.5), which would drop look-alike orders that differ on the action, e.g. "book the Fresno load Friday" vs "cancel the Fresno load Friday"; a higher one, which drops almost nothing | At 0.7, 0 of 553 rows were dropped in the full run, and 0 of 101 in two smoke runs (measured). Reading the top pairs, they are different orders that share a template and subject-line format (a quote vs. a new order, different lanes and dates), not rewordings of one order, so lowering the threshold would delete real test cases rather than paraphrases | If the dropped pairs at a threshold differ only in wording, lower it to remove paraphrases; if they differ on an action, date or temperature, the threshold is removing real test cases, so keep or raise it | Character n-grams miss paraphrases ("10 pallets" vs "ten pallets") and over-match rows that share long boilerplate like email signatures and Gmail headers; embeddings (Week 3) would catch the first case |
| 2 | Generate in two runs: ENTERABLE crosses all five axes (540 combinations); ROUTE_TO_PERSON crosses only arrival × reason (12) | Crossing every axis (~2,400 combinations); trimming values until the full cross was affordable; one combined dict | Routing is what the decline run tests and field extraction is already covered by ENTERABLE, so crossing declines with temperature and date adds cost, not coverage. | 2 | Generation settings: 2 seeds per prompt matched to the arrival format; 1 row per call; max_tokens 16000; one retry for a combination that returns nothing; provider-default sampler and reasoning | Always showing the first 3 goldens; 3 rows per call; max_tokens 8000 | The first 3 goldens never showed the PO-attachment format and anchored every row on one customer's layout.
